# 用户侧 Plugin 设计

用户侧 Plugin 让 Agent 读取共同档案与相关经历，并记录本次明确表达或核实的信息。它由 Skill + MCP 构成；存储位置及认证由用户的运行环境提供，第一版访问配置指定的 GitHub 仓库。

本文讨论用户侧的实现边界，遵守 [共同约定](../README.md)。批量压缩与年龄遗忘由独立的 [整理侧 Skill](memory-consolidation-design.md) 执行。

## 职责与插件构成

| 参与部分 | 职责 |
| --- | --- |
| 记忆使用 Skill | 指导何时读取、哪些内容可记录，以及如何增删改查不同类型记忆 |
| MCP | 包装绑定池的读取、检索、更新、历史查询与结果确认；校验格式和版本，访问 GitHub，维护本地副本 |
| Agent 运行环境 | 启动 MCP，提供配置、git / gh CLI 及其凭据，运行模型和 Skill |
| 用户的 GitHub 仓库 | 保存当前记忆和 Git 提交历史，提供实际访问权限 |
| 记忆整理 Skill | 随同一 Plugin 分发，在单独的整理任务中使用同一套工具 |

MCP 不判断聊天中的决定是否已确认，也不生成语义摘要；这些由执行相应 Skill 的 Agent 完成。MCP 可以校验格式、范围和版本，不能靠格式校验证明内容真实。

以下是源树示意，发布目录与 Skill 名称尚未确定：

~~~text
Plugin
├── 插件描述文件
├── skills/
│   ├── 记忆使用 / SKILL.md
│   └── 记忆整理 / SKILL.md
├── MCP 启动描述
└── MCP 可执行入口及依赖
~~~

两份 Skill 不硬编码仓库、认证或设备路径。Plugin 升级保留用户绑定与池数据；格式升级另行识别、验证和迁移。

## 绑定配置与运行环境认证

每个 Agent 配置固定绑定一个池。配置由用户维护，概念示例如下；实际字段名在实现时确定：

~~~json
{
  "repository": "owner/agent-memory",
  "branch": "main",
  "expected_pool_id": "pool-example"
}
~~~

配置写明仓库、分支和预期池身份；不存 Token。普通记忆工具只操作绑定池，不接受任意仓库地址、凭据或任意 shell 命令。池身份不匹配时停止操作并明确反馈。

认证复用运行环境的 git / gh CLI：gh 使用其已有登录或环境变量；git 使用环境已配置的 HTTPS credential helper 或 SSH 认证。gh 的环境变量优先级为 GH_TOKEN、GITHUB_TOKEN、已保存登录；git 可通过 gh auth setup-git 使用 gh 作为 credential helper，但不能假定两者的认证天然相同。[gh 环境变量](https://cli.github.com/manual/gh_help_environment)、[gh auth setup-git](https://cli.github.com/manual/gh_auth_setup-git)

MCP 不把凭据放入记忆、日志或工具结果，不把认证 Token 交给模型。环境变量的注入与 CLI 凭据准备属于宿主接入；具体操作路径是 git 命令还是 gh api，留待实现讨论。第一版无需另外建立认证服务。

仓库可见性由用户选择，接入只检查实际操作能力：读取需要可读；新增、修订、删除和整理需要写入权限及绑定分支允许提交。只读身份可以读池，不能保存；分支规则拒绝提交时返回失败。[GitHub 仓库](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories)、[分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

建议每个运行环境启动本地 stdio MCP，共享远端数据。若未来选择远程 MCP，需要另行设计客户端到 MCP 的认证；它与存储认证是不同接口。[MCP 认证规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

## Skill 的日常行为

1. 新会话或话题明显变化时，读取当前协作档案，匹配项目或主题，再检索相关当前经历。无法确定上下文时澄清，避免按本地路径重复建项目。
2. 发现用户明确表达、纠正或已核实的重要结果时，提炼必要内容。通用方法由知识库维护，记忆只保存具体背景、原因、结果及引用。
3. 根据类型新增或修改档案、经历和必要来源。明确纠正标记取代关系；未明确取代的矛盾保留，相关时澄清。
4. 通过 MCP 提交，按真实返回结果说明是否保存。用户明确要求删除时删除当前内容，并区分这与历史清理。
5. 仅在用户明确要求回溯时读取历史。普通召回不足时说明当前缺失，不自动查历史。

当前档案表达稳定协作关系；经历保存项目或主题背景和决定。Agent 不需要保存完整聊天，也不承担日常批量整理旧池的任务。本次实际使用的旧信息可形成新经历，其时间与来源按共同约定记录。

从池召回的内容作为带来源的数据使用，不能自行改变 Plugin 绑定、工具权限或 Skill 规则。Skill 遵循仍依赖 Agent；提供 MCP 工具不保证每个会话或决定都能被记录。

## MCP 的能力边界

下表描述能力，尚未固定工具名称或参数：

| 能力 | 输入与可观察结果 |
| --- | --- |
| 读取池状态与当前档案 | 返回池身份、版本、策略与可用性 |
| 匹配上下文、检索与读取当前记忆 | 返回有限内容、来源线索及读取版本；限制单次输入和返回量 |
| 批量新增、修订、删除 | 输入基准版本和变更；验证格式及关系后提交，返回接受版本或失败原因 |
| 查询操作结果 | 按操作标识确认曾否接受提交，区分成功、未接受与仍无法确认 |
| 查询历史 | 在用户明确要求下按上下文、时间及版本限制范围，标明当时版本和覆盖范围 |

首期检索从稳定上下文匹配与全文搜索开始。本地索引可重建，向量库或知识图谱是否必要由实际召回效果判断。

整理侧复用同一套读取和批量修改能力，所需的分页、有限材料读取和容量信息一并纳入工具设计；无需另建摘要写入通道或后台模型服务。初始化、绑定变更、策略修改及历史清理使用单独管理入口。

## 提交与失败处理

一次修改基于读取版本 H，形成一批文件变更及以 H 为父版本的新提交，再以非强制方式推进绑定分支。git push 默认拒绝会丢失分支历史的非快进更新；gh api 也可用 force=false 更新 ref。具体路径尚未选择，但都要防止旧计划覆盖并发提交。[Git push](https://git-scm.com/docs/git-push)、[GitHub refs](https://docs.github.com/en/rest/git/refs)

冲突后重新读取并核对内容，不能盲目把旧摘要重放到新版本。独立新增可合并，语义矛盾按共同约定保留。摘要与对应删除放在同一提交中。

调用方在发送远端提交前取得或指定操作标识，并能从本次任务记录恢复它；不能只在最终响应中才返回标识。标识记录在提交元数据等机制中，避免在当前池另建不断增长的回执文件。发送后结果不明时沿用原标识确认，再决定是否重试。结果确认不向模型召回历史正文。

| 情况 | 工具结果与恢复方式 |
| --- | --- |
| 在线读取成功 | 返回确认的版本，并刷新本地副本 |
| 离线读取且有副本 | 返回副本版本与同步时间，标明未刷新远端 |
| 无副本、读取失败或池格式无效 | 说明不可用或具体错误；若提供旧的可用副本，明确标识 |
| 发送前离线、认证或权限失败 | 未保存，不排队；修复后重新发起 |
| 格式无效或输入过大 | 未保存；指出应修正的内容 |
| 基准版本冲突 | 不覆盖；重读、重新核对后提交 |
| 远端接受提交 | 已保存，返回接受版本 |
| 发送后超时或响应丢失 | 结果未知，先按操作标识确认，避免重复记录 |
| 远端成功但本地刷新失败 | 已保存、本地副本仍旧；只修复副本 |
| 历史查询失败或范围不完整 | 说明失败或实际覆盖范围，不声称完整历史无结果 |

本地草稿和未推送提交不算已保存的记忆，也不组成离线待同步队列。新设备需要在线读取一次，才具备离线读取副本；远端删除同步后从当前索引移除，已经进入会话上下文的内容不会因此消失。

历史回溯只覆盖 Git 实际保留的版本，查询和返回量受限；离线查询只覆盖已有历史缓存。恢复需要的旧内容走正常写入规则，不回滚整个池。[Git log](https://git-scm.com/docs/git-log)

## 建池与接入

创建新池或连接已有池是一次性流程：准备仓库与运行环境凭据，生成或核对池身份、格式和策略，写入绑定配置，再在线读取并建立本地副本。另一设备绑定同一仓库，无需迁移原客户端聊天记录。

新池按用户指定的可见性创建，生成独立 ID 与空内容；已有仓库先检查池结构，禁止用空池覆盖已有内容。仓库创建权限与内容写入权限分别检查。仓库已创建但初始化失败时报告部分结果，支持继续初始化，不擅自删除仓库；空仓库需先建立首个提交。[GitHub refs](https://docs.github.com/en/rest/git/refs)

第二个隔离池复用同一流程。更换隔离池需要新会话，避免已召回的旧池内容继续留在上下文中。未来迁移以共同格式为基础，后端特有的历史能力单独处理。

## 客户端适配与实施验收

首批面向 Codex 和 GitHub Copilot。官方文档提供包含 Skills 与 MCP 的插件机制，可据此设计同一源树；安装方式、MCP 执行位置与环境注入按实际客户端验证，不能从文档支持推断所有 CLI / App 版本已实测兼容。[Codex 插件](https://developers.openai.com/plugins/build/plugins)、[Copilot CLI 插件](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference)、[VS Code 插件](https://code.visualstudio.com/docs/agent-customization/agent-plugins)

远程或定时运行环境不能自动使用另一台设备的 gh 登录；需要在其实际执行位置提供配置、CLI 和凭据。环境注入按宿主机制处理。[Copilot CLI MCP](https://docs.github.com/en/enterprise-cloud%40latest/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers)、[VS Code MCP](https://code.visualstudio.com/docs/agent-customization/mcp-servers)

实施后重点验收：

- Codex 写入已确认偏好与决定，Copilot 从同池接续背景。
- 两设备独立新增与并发纠正不丢失内容；整理任务不能覆盖期间的新写入。
- 只读身份、分支限制、离线状态与响应丢失均返回真实结果。
- 合法人工编辑可读取，损坏格式或错误绑定明确反馈。
- 普通召回不读历史，明确要求后才返回限定范围的旧版本。
- 用真实会话观察 Skill 的执行与漏执行情况。

该侧实施时单独确定工具参数、共同格式字段与目录、git / gh 操作路径、缓存方式、实现语言、发布渠道及客户端版本范围；容量接纳规则与整理侧共同确定。
